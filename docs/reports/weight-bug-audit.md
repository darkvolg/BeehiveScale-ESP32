# BeehiveScale — аудит нестабильного веса (v4.1)

**Дата:** 2026-05-03
**Аудитор:** Embedded Firmware Engineer
**Платформа:** ESP8266 NodeMCU Lolin v3, HX711, прошивка v4.1
**Эталон сравнения:** `Bee_Lite_D1_v1.1-1000gr.ino` (Як Иваныч) — работает в реальной пасеке

---

## TL;DR — короткий вердикт

**Корневая причина 90% проблем — выбор пинов GPIO16 (DT) и GPIO1 (SCK) для HX711.**

Это не «софт-баг который можно подкрутить». Это **аппаратный антипаттерн**. Любой софтверный фильтр поверх такой подложки даёт временное улучшение, потом снова срыв — что и описывает пользователь словами «то калибруется, то ерунду показывает».

Эталон (Як Иваныч), который работает у пчеловода в реальном улье, использует **DT=GPIO14 (D5), SCK=GPIO12 (D6)** — стандартные SPI-совместимые пины ESP8266 без boot-strap функций и без аппаратных особенностей.

**Без перепайки HX711 на GPIO14/12 — софт никогда не будет работать стабильно.** Дальше в отчёте даны программные баги для добивания, но это второстепенно.

## 1. Корневая причина

### 1.1 Главный виновник: пины HX711

`BeehiveScale.ino:34-37`

```c
#define DT_PIN          16   // GPIO16
#define SCK_PIN          1   // GPIO1 = UART0 TX
#define BUTTON_PIN       0   // GPIO0 = boot-strap (FLASH/RUN)
#define MENU_BTN_PIN     2   // GPIO2 = boot-strap (boot mode)
```

**Что не так с GPIO16 как DT (DOUT) у HX711:**

1. **GPIO16 не имеет внутреннего pull-up.** ESP8266 SDK позволяет только `INPUT` или `INPUT_PULLDOWN_16` для этого пина. Сам код это признаёт (`Scale.cpp:11-15`):
   ```c
   // GPIO16 не поддерживает INPUT_PULLUP на ESP8266
   if (dtPin != 16) {
     pinMode(dtPin, INPUT_PULLUP);
   }
   ```
   То есть авторы **знали** про проблему и всё равно оставили GPIO16. В итоге линия DOUT висит без подтяжки. HX711 в idle при готовых данных тянет линию LOW, но между считываниями DOUT в высокоимпедансном состоянии — ловит наводки.

2. **GPIO16 — отдельная RTC GPIO** (не общая с GPIO0–15). Имеет повышенный jitter переключения, не оптимизирован для bit-banging высокочастотных протоколов. HX711 требует точной выборки фронта DOUT (t_DR < 0.1 µs до фронта SCK).

3. **GPIO16 используется для wake-from-deep-sleep** (соединяется с RST для пробуждения). Если у тебя в проекте `SLEEP_MODE_DEEP_SLEEP` — конфликт фатальный (DT-провод HX711 уйдёт на RST через перемычку wake).

**Что не так с GPIO1 как SCK:**

1. **GPIO1 = UART0 TX.** На boot ESP8266 шлёт по нему bootloader-сообщения на 74880 baud, потом `Serial.begin(115200)` снова занимает пин. Любой байт по UART = импульс на SCK HX711 = команда тактирования датчика мусором.

2. Код пытается это обойти (`BeehiveScale.ino:176`):
   ```c
   Serial.end();              // Освободить GPIO1 (TX) перед HX711
   scale_init(scale, DT_PIN, SCK_PIN);
   ```
   Но это работает только **после** `setup()`. Между ROM-bootloader (74880 baud) → bootloader на флеш → setup() → `Serial.begin(115200)` (`BeehiveScale.ino:140`) → `Serial.end()` (`BeehiveScale.ino:176`) проходит **сотни миллисекунд** с активным UART TX. Всё это время SCK HX711 получает мусор. После каждого reboot HX711 может оказаться в произвольном внутреннем состоянии (не gain=128, не channel A).

3. После `Serial.end()` любой случайный `Serial.print(...)` в коде (а их в файле десятки штук — `Serial.println(F("[HX711] Watchdog: reinit"))` и т.п.) **пытается** писать в UART. На ESP8266 после `end()` это no-op для пользователя, но низкоуровневый драйвер UART может реактивировать пин. Авторы это понимают (`BeehiveScale.ino:83-84`), но риск остаётся.

4. **GPIO1 — boot-strap.** Должен быть HIGH на старте для нормальной загрузки. HX711 SCK в idle = LOW. Если плата перезагружается в момент когда HX711 держит SCK низким (через подтяжку или из-за power_down состояния) — boot падает в UART download mode → плата не стартует.

**Что не так с GPIO0/GPIO2 как кнопки:**

- **GPIO0** = boot mode select. LOW при включении = flash mode. Если пользователь держит «главную кнопку» при включении/auto-wake — плата не загрузится.
- **GPIO2** = тоже boot-strap (должен быть HIGH). LED_BUILTIN на NodeMCU. Кнопка с подтяжкой к GND через нажатие — ОК для работы, но при boot нажатая кнопка ломает загрузку.

### 1.2 Почему симптом именно «то калибруется, то ерунду показывает»

При калибровке (`perform_calibration`, BeehiveScale.ino:1169–1324) пользователь:
1. Жмёт кнопку → HX711 тарируется (raw average ~ const).
2. Кладёт груз → HX711 даёт `raw = scale.get_value(20)` за ~2.5 сек.

Если в эти 2.5 сек на DOUT GPIO16 нет помехи — **калибровка проходит, cf корректный, сохраняется в EEPROM.**

После калибровки начинается рабочий режим: чтение раз в 800 мс (`process_weight`), 5-6 sample averaging, EMA-фильтр. Здесь GPIO16 ловит наводку → отдельные читки сильно отклоняются → сначала срабатывает spike-filter (отбрасывает), но при 5 подряд rejections (`BeehiveScale.ino:616-620`) — **сбрасывается EMA**, и следующий «зашумлённый» отсчёт принимается как новая база. Дальше:
- Watchdog HX711 (`BeehiveScale.ino:341-366`): если DRDY от GPIO16 даёт ложные «не готов» 6 раз подряд → **reinit датчика**, **EMA снова сброшен**, **smoothedWeight = 0**.
- В Scale.cpp:48-59 после каждого `get_units()` идёт **ещё 3 raw чтения** для проверки залипания. На зашумлённом GPIO16 эти 3 raw почти никогда не будут идентичны → **ложная нестабильность не выявляется**, но удваивается время выборки и сама вероятность поймать наводку.

То есть: **калибровка случайно проходит → пара минут работы → один пик → сброс EMA → watchdog → reinit → новые случайные показания → визуально «ерунда»**. Полностью объясняет жалобу.

### 1.3 Доказательство: эталон работает на других пинах

Як Иваныч `Bee_Lite_D1_v1.1-1000gr.ino:124-125`:
```c
const int LOADCELL_DOUT_PIN = 14;   // D5 — обычный GPIO с pull-up
const int LOADCELL_SCK_PIN  = 12;   // D6 — обычный GPIO
```
Никаких boot-strap, никаких UART TX, никаких GPIO16. Прошивка примитивная, без spike-filter, без EMA, без watchdog HX711, без power-cycle логики — и при этом **показывает вес правильно**, потому что подложка стабильная.

|---|---|---|---|

| **Главная кнопка** | GPIO0 (boot-strap FLASH) | — (одна кнопка GPIO2) | Нажатие при boot → flash mode |

| **WiFi STA + Web UI + OTA** | Да, всегда | Не используется | Доп. шум на питании, но не главное |
| **Питание HX711** | От ESP8266 3V3 (предположительно) | От ESP 3V3 | Одинаково |
| **Подтяжка DOUT** | Нет (GPIO16 не умеет INPUT_PULLUP) | Внутренняя INPUT_PULLUP | **Главное аппаратное различие** |

## 3. Найденные баги (приоритизированно)

### P0 — БЛОКЕРЫ. Без этого весы стабильно работать не будут.

#### P0.1 — Перепайка HX711 на GPIO14 (D5) и GPIO12 (D6)

**Файл:** `BeehiveScale/BeehiveScale.ino:34-35`
**Сейчас:**
```c
#define DT_PIN          16
#define SCK_PIN          1
```
**Должно быть:**
```c
#define DT_PIN          14   // D5 на NodeMCU Lolin v3
#define SCK_PIN         12   // D6 на NodeMCU Lolin v3
```

**Что это даст:**
- INPUT_PULLUP на DT работает → DOUT держится HIGH между чтениями, наводки в разы меньше.
- SCK не пересекается с UART → bootloader-мусор не попадает на HX711.
- Можно вернуть Serial для отладки в production без `Serial.end()` костыля.

**Хардварная работа:**
1. Перепаять провод HX711 DT с пина D0 (GPIO16) на D5 (GPIO14).
2. Перепаять провод HX711 SCK с пина TX (GPIO1) на D6 (GPIO12).
3. Перепрошить с обновлёнными `#define`.

**Это №1 приоритет. Без этого пункта дальше идти бессмысленно.**

#### P0.2 — Перенести кнопки с boot-strap пинов

**Файл:** `BeehiveScale/BeehiveScale.ino:36-37`
**Сейчас:** `BUTTON_PIN=0`, `MENU_BTN_PIN=2`. Оба boot-strap.
**Должно быть:** одна или обе кнопки на GPIO13 (D7) и GPIO15 (D8 — НЕТ, тоже boot-strap, должен быть LOW). Свободные «безопасные» пины на NodeMCU после перепайки HX711:
- D7 = GPIO13 — свободен, безопасный, INPUT_PULLUP работает.
- D3 = GPIO0 — boot-strap, но если кнопка отжата на старте — ОК (текущий BUTTON_PIN, можно оставить **только если** пользователь железно гарантирует что не держит её при включении).
- D4 = GPIO2 — boot-strap, рискованно. Нажатие при включении = плата не грузится. **Перенести.**

**Рекомендация:** одна кнопка на GPIO13 (D7), вторая — оставить на GPIO0 (D3) с предупреждением «не держать при включении». Лучше — обе на безопасные пины (D7 + ещё один свободный после перепайки HX711). После переноса HX711 на D5/D6 свободны: D0 (GPIO16, можно для wake), D7 (GPIO13), TX (GPIO1, можно вернуть Serial), RX (GPIO3).

#### P0.3 — Серия `set_scale()` после WiFi.init — карго-культ или признак реальной поломки

**Файл:** `BeehiveScale/BeehiveScale.ino:200-213`
```c
if (sys.sensorReady) {
  scale.set_scale(sys.calibrationFactor);
  scale.set_offset(sys.offset);
}
yield();
sys.wifiOk = wifi_init();
yield();
// После WiFi восстанавливаем параметры HX711 (на ESP8266 WiFi.mode() может сбросить GPIO)
if (sys.sensorReady) {
  scale.set_scale(sys.calibrationFactor);
  scale.set_offset(sys.offset);
}
```

`scale.set_scale()` и `scale.set_offset()` — это просто запись в **поля C++ объекта `HX711` в RAM**, они не трогают железо. WiFi.mode() не может сбросить значения C++ полей. Этот комментарий — миф (вероятно, кто-то увидел странные показания после WiFi и добавил «на всякий случай»). Если это действительно помогало — значит RAM повреждается, что косвенно подтверждает гипотезу про переполнение стека из-за WiFi+OTA+Web+Telegram+TG_REPORT в сетапе на ESP8266 с 80 KB RAM.

**Действие:** убрать второй вызов после `wifi_init()`. Если действительно начнёт ломаться — проверить heap (`ESP.getFreeHeap()`) на старте до и после `wifi_init()` — может быть переполнение стека/heap.

### P1 — Сильные улучшения точности и предсказуемости.

#### P1.1 — `scale_read_weight()` делает 3 лишних raw чтения после `get_units()`

**Файл:** `BeehiveScale/Scale.cpp:36-63`

После каждого валидного `get_units(5)` (5 чтений × ~100 мс = 500 мс) идут ещё 3 `scale.read()` (× ~100 мс = 300 мс) для anti-stuck. **Это удваивает окно выборки, повышает вероятность поймать сетевую наводку, и не имеет смысла:**
- Если `get_units(5)` вернул NaN/мусор — нужно power-cycle сразу, а не делать ещё 3 чтения.
- Если 5 sample отработали успешно — датчик не залип. 2 одинаковых raw подряд при стабильном грузе на качественной электронике — **норма**, а не патология. Даже 3 одинаковых при нагрузке без вибраций — возможно.
- Сама логика `if (raw1 == raw2 && raw2 == raw3)` ловит только полный stuck, при котором уже `get_units(5)` дал бы 5 одинаковых ошибок.

**Предложение:** убрать блок anti-stuck из `scale_read_weight()`. Перенести проверку залипания в watchdog в `loop()` (он там уже есть и срабатывает по таймауту).

#### P1.2 — Spike-filter 5 кг + сброс EMA после 5 rejections

**Файл:** `BeehiveScale/BeehiveScale.ino:610-622`

Текущая логика: при 5 подряд отклонённых spike → `emaInitialized = false`, следующая выборка принимается как база. На шумном GPIO16 это **постоянно** срабатывает: серия наводок → 5 rejections → сброс → шумный отсчёт становится «правильным». После перепайки на GPIO14 порог можно снизить до 2-3 кг (нормальная пасечная динамика — плавная), а сброс EMA сделать через 10 rejections и **не принимать первый отсчёт после сброса как истину** (проверять стабильность 3 чтений подряд).

#### P1.3 — Watchdog HX711 reinit раз в 30 сек

**Файл:** `BeehiveScale/BeehiveScale.ino:341-366`

`scale.is_ready()` проверяется каждые 5 сек. После 6 неответов (30 сек) — `scale_init()` + сброс EMA. На GPIO16 без pull-up `is_ready()` может давать ложные FALSE из-за плавающего DOUT. Каждый reinit:
- Сбрасывает EMA (`emaInitialized = false`)
- Сбрасывает `smoothedWeight = 0.0f`
- На ~500 мс блокирует чтение веса

После перепайки эта проблема исчезнет автоматически, но стоит добавить counter: `reinitCnt`. Если за час > 3 reinit → значит что-то системно не так, писать в лог + предупреждение в UI.

#### P1.4 — `process_weight()` с интервалом 800 мс не успевает за `get_units(5)` + 3 raw

**Файл:** `BeehiveScale/BeehiveScale.ino:577`
```c
if (millis() - lastReadTime < 800UL) return;
```

`get_units(5)` ~ 500 мс + 3 raw ~ 300 мс = 800 мс. То есть мы читаем HX711 **непрерывно**, без паузы. Это:
- Не оставляет окна для loop() на обработку кнопок, веба, OTA.
- Прогревает HX711 (он начинает греться внутри → температурный дрейф).
- Не даёт фильтру усредниться по реально независимым выборкам (HX711@10Hz даёт независимые сэмплы каждые 100мс, у нас они подряд → не усредняется шум сети 50 Гц).

**Предложение:** интервал 2-3 сек (как у Як Иваныча — 3 сек и работает) + samples=10 (без anti-stuck из P1.1) → 1 секунда выборки + 1-2 секунды покоя. Это снизит температурный дрейф, даст веб-серверу время отвечать на запросы, и упростит EMA (выборки реально независимы).

#### P1.5 — Двойная вызов `set_scale()` / `set_offset()` после WiFi (см. P0.3)

Поднят выше как P0.3 — но именно как софтовый пункт он P1. P0 этот пункт по другой причине: он симптом возможного повреждения памяти.

#### P1.6 — Калибровка не сохраняет offset стабильно

**Файл:** `BeehiveScale/BeehiveScale.ino:1232-1245`

Внутри `perform_calibration()` делается ручной tare на 10 sample, потом offset сохраняется как `sum/10`. На шумном GPIO16 std deviation 10 sample = десятки тысяч единиц → offset уплывает на каждой калибровке на сотни грамм. После перепайки этот шум упадёт, но имеет смысл увеличить число samples до 30 и/или применить медиану вместо среднего (чтобы выбросы не тянули offset).

#### P1.7 — Несогласованность времени между двумя tare-блоками

**Файлы:**
- `perform_taring`: `BeehiveScale.ino:1117-1126` — TARE_SAMPLES=20, wait_ready 500 мс на каждый.
- `perform_calibration`: `BeehiveScale.ino:1232-1243` — TARE_SAMPLES=10, без проверки результата `wait_ready_timeout`.

Калибровочный tare делает в 2 раза меньше выборок и не проверяет ready. На шумной линии — нестабильный ноль → нестабильный cf. Унифицировать на 20 sample + проверку ready.

#### P1.8 — Калибровочный raw < 1000 даёт power-cycle и retry с тем же offset

**Файл:** `BeehiveScale/BeehiveScale.ino:1271-1296`

Если первое чтение под грузом дало raw < 1000 ADC units (т.е. груза почти не видно) — power_cycle, восстановление offset, retry. Это разумно. **Но:** проверка `if (fabsf(raw) < 1000.0f)` срабатывает и при правильно подключённом тензодатчике с малым весом (300 г груз × коэффициент тензо ~ может дать <1000 raw на некоторых ячейках). У Як Иваныча без такой проверки — он принимает любой raw. Лучше дать пользователю в UI выбрать вес калибровки и не блокировать по абсолютному порогу. Или поднять порог до 100 (разумное «совсем мало»).

#### P1.9 — `web_get_calib_weight()` валидирует только 100..5000 граммов

**Файл:** `BeehiveScale/Memory.cpp:38`

Если пользователь хочет калиброваться на 10 кг гире (для 200 кг улья — нормальная практика) — UI отклонит. После проверки — поднять верхнюю границу до 50000 г (50 кг).

### P2 — Косметика, надёжность, читаемость.

#### P2.1 — Удалить комментарий-миф «WiFi.mode() может сбросить GPIO»

`BeehiveScale.ino:209` — вводит в заблуждение будущих контрибьюторов.

#### P2.2 — Удалить дублирование вызовов `Serial.println` после `Serial.end()`

После `Serial.end()` (BeehiveScale.ino:176) Serial используется десятки раз: `Serial.println(F("[HX711] Watchdog: reinit"))` и т.д. Это не падает, но выглядит грязно. После перепайки на GPIO12/14 — Serial можно вообще не закрывать, и весь этот код станет валидным.

#### P2.3 — EEPROM cf без CRC

**Файл:** `BeehiveScale/Memory.cpp:60-78`

Magic byte `0xA5` без CRC. При повреждении одного байта в float (4 байта) — magic уцелеет, cf станет мусором. Валидация `factor < 100.0f || factor > 100000.0f` ловит большинство случаев, но не все (например, 5000.0f → корректное cf, 12345.6 после повреждения тоже в range). Добавить CRC8 на блок calibration — тривиально, надёжность выше.

#### P2.4 — Auto-zero deadband 0.001 кг бесполезен после EMA

**Файл:** `BeehiveScale.ino:597-599`
```c
if (fabsf(raw) < 0.001f) raw = 0.0f;
```
EMA после применения сделает значение почти-нулевым, но не строгий 0. На UI будет видно `0.00 kg` (truncated). Этот deadband не решает реальную задачу — стоит убрать или поднять до 0.05 кг (реальный шум весов).

#### P2.5 — `lastSavedWeight` сохраняется при `WEIGHT_SAVE_THR=0.05f` каждые 5 минут

При шумном весе ±0.1 кг это **постоянная** запись в EEPROM. EEPROM на ESP8266 — flash, ресурс ~10000 циклов на сектор. 12 записей/час × 24 ч = 288/сутки → износ за ~35 дней. Это серьёзно. После перепайки шум уменьшится, но всё равно стоит:
- Поднять WEIGHT_SAVE_THR до 0.2 кг.
- Записывать только при стабильном весе (`weightStable == true`).
- Или вообще писать раз в сутки (только при сильных изменениях).

#### P2.6 — Возможное переполнение стека на ESP8266

ESP8266 имеет **4 KB стек** на main task. В loop() задействованы: `WebServerCompat`, `ArduinoJson` (с буферами), `LittleFS`, `Telegram` (HTTP клиент), `OTA`, `mDNS`, NTP. Если в любой момент один из них рекурсивно зайдёт глубоко — stack overflow → reset → пользователь видит «весы перезагрузились и забыли калибровку». Такой ребут может быть «тихим» (без сообщения).

**Действие:**
- Замерить `ESP.getFreeContStack()` в loop() и в самых глубоких callback (например, веб handler).
- Если < 1 KB stack free — это плохо. Нужно упрощать (выкинуть Telegram или OTA или мdnS).

## 5. Тест-план (без улья)

### Тест T1 — Стабильность в покое (без груза)

1. Прошить, дать прогреться 5 минут (HX711 имеет температурный warm-up).
2. Тарировать через кнопку.
3. Записать показания через веб-UI каждые 30 сек × 30 минут.
4. **Критерий PASS:** разброс < 0.05 кг (50 г), нет single spikes > 0.2 кг.
5. **Критерий FAIL (и нужно ещё разбираться):** разброс > 0.2 кг или хоть один скачок > 1 кг.

### Тест T2 — Калибровка повторяемость

1. Положить на весы 1 кг гирю (или известный вес — 2 бутылки воды по 0.5 л = 1 кг).
2. Калибровать через долгое нажатие кнопки.
3. Записать `calibrationFactor` (виден на экране 5 «Status» или в веб-UI).
4. Снять груз, **перезагрузить** ESP (физический reset, не reflash).
5. Снова положить ту же гирю.
6. **Критерий PASS:** показания 1.00 ± 0.02 кг (2%).
7. Повторить калибровку 5 раз с reboot между ними.
8. **Критерий PASS:** cf отличается от первого замера < 5%.

### Тест T3 — Линейность

1. После T2 (откалибровано на 1 кг).
2. Положить 0.5 кг → ожидание 0.50 ± 0.02 кг.
3. Положить 2 кг → ожидание 2.00 ± 0.04 кг.
4. Положить 5 кг → ожидание 5.00 ± 0.10 кг.
5. **Критерий PASS:** все три точки в диапазоне.
6. **Критерий FAIL:** значит тензодатчик дохлый или питание HX711 нестабильное. Уже не софт-проблема.

### Тест T4 — Долгая работа

1. После калибровки положить 2 кг гирю.
2. Оставить на 12 часов (на столе, не в улье).
3. Просмотреть лог веса (в веб-UI).
4. **Критерий PASS:** все значения 2.00 ± 0.05 кг, нет «прыжков» > 0.2 кг, нет EMA-сбросов в Serial.
5. **Критерий FAIL:** есть прыжки или дрейф > 0.1 кг/час → ловить дальше (питание / тензо / температура).

### Тест T5 — WiFi/OTA не ломает вес

1. После T4 — пусть гиря лежит.
2. Скачать backup через веб-UI.
3. Залить OTA новую сборку (тестовую, с увеличенным `Version.h`).
4. После OTA — проверить вес. **Критерий PASS:** показания не изменились более чем на 0.05 кг.

### Тест T6 — Boot stability (P0.2 проверка)

1. Зажать обе кнопки.
2. Дёрнуть питание.
3. **Критерий PASS:** плата стартует, на экране splash + showing weight (≈0).
4. **Критерий FAIL:** плата висит в bootloader (UART сообщения «waiting for download...») или в режиме flash mode → нужно P0.2.

## 6. Что **не** является корневой причиной (опровержение подозрений из ТЗ)

- ✅ **Формула калибровки `cf = raw / (knownGrams/1000)`** — корректна и согласуется с тем как `HX711::get_units()` возвращает значение в килограммах (если cf откалиброван так, чтобы 1 ADC unit = 1/cf кг). Магического `×100` Як Иваныча у нас нет, потому что мы храним cf как float, а не как int16. Не переписывать.
- ✅ **EEPROM `EEPROM.put(float)`** — портативно через `memcpy`, не имеет UB. В Як Иваныча ровно противоположная проблема (`(float*)&x` — UB), нам её не делать.
- ✅ **Sensor watchdog в loop()** — сама идея здравая, но при перепайке на GPIO14/12 ложных срабатываний не будет.
- ✅ **Spike-filter 5 кг** — после перепайки порог разумный (улей не может прыгать на 5 кг за 800 мс, а пчёлы массой даже сильно дать не могут).
- ⚠️ **Двойной `set_scale()` после WiFi.init** — не корневая, но тревожный симптом. См. P0.3.

## 7. Финальный вердикт пользователю

> Главное: пины. **D0 и TX — категорически не подходят для HX711.** Як Иваныч не зря использует D5/D6 — это стандарт. После перепайки и обновления `#define` весы должны заработать сразу. Если не заработают — проблема в пайке тензодатчика или питании, и тогда уже железная диагностика (мультиметр на VCC HX711 при WiFi-передаче, осциллограф на DOUT/SCK).
>
> Софт у нас сложнее чем у Як Иваныча и наворочен (EMA, watchdog, spike-filter, web, OTA, telegram). После перепайки можно даже отключить все «защиты» и весы будут показывать вес — это лучший тест на чистоту железа.
>
> На полке лежащие модули — собирай, перепаивай, ставь в улей. Прошивку правлю Я (после твоего «ОК»), но без хардвара — никакая прошивка не спасёт.
